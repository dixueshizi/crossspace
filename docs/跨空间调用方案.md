# 跨空间调用方案（ColorOS 14 / 15 / 16）

> 目标：主空间的自动化工具把微信（以及支付宝等）拉起 / 启动到系统分身 999、自建 10–30 号空间。
> 结论先行：**走 `am start --user N` 的转发器即可，不需要 LSPosed，也不需要 root**。
> 本文件同时是交付说明：实现位于仓库内 `crossspace/` 目录。

---

## 1. 结论（TL;DR）

| 问题 | 答案 |
|---|---|
| 10–30 号 `ymyx` 是什么 | **标准 Android 多用户**（`pm list users` 里是独立 `UserInfo`，按 user 独立装包），不是 VirtualApp 类容器 |
| 999 是什么 | clone profile（`MultiApp`），与 user 0 同 profile group，但启动仍按 userId 走 |
| 需不需要 root | **不需要**。`adb shell`（uid 2000，平台签名）就能 `am start --user N`；有 root 只是多一条兜底 |
| 需不需要 LSPosed | **不需要**。LSPosed 只在“第三方工具完全无感、要自动改写它自己的 Intent”时才需要 |
| 跨 ColorOS 14/15/16 | 主线方案**天生跨版本**，因为 `am` 是 shell 层命令，不经过 OEM 私有 API |
| 实测状态 | 已在 ColorOS 15（OnePlus PJX110）跑通微信→999、支付宝→10；14/16 待实机复测 |

原 ColorLink 模块在 ColorOS 15 上**连 hook 都不装**（`s()` 只认 14 和 16），这就是“调用不起”的第一层原因；我们这条路线不受它影响。

## 2. 立刻可用：转发器 + 调用范式

### 2.1 形态

一个设备端纯 shell 脚本 + 一个 Windows 薄封装：

```
crossspace/
├── crossspace.sh     设备端 CLI（root 或 shell 身份都能跑）
├── crossspace.ps1    Windows 封装（adb 调用 + 自动 su 兜底）
├── apps.conf         应用名单 / 页面映射（可扩展 QQ、抖音）
└── README.md         一页纸使用说明
```

设备端固定落在 `/data/local/tmp/crossspace/`。

### 2.2 部署（一次）

```powershell
cd crossspace
.\crossspace.ps1 -Deploy
```

### 2.3 调用范式（可直接粘）

**A. PowerShell / 批处理（PC + USB）**

```powershell
.\crossspace.ps1 -User 999 -App wx -Page home          # 微信主界面 → 999
.\crossspace.ps1 -User 10  -App alipay -Page home      # 支付宝主界面 → 10
.\crossspace.ps1 -User 999 -App wx -Page scan          # 微信扫一扫 → 999
.\crossspace.ps1 -User 15  -App wx -Page sns           # 微信朋友圈 → 15
.\crossspace.ps1 -All -App wx -Page home -Range 10-30  # 批量
```

**B. 自动化工具里的 shell 步骤（推荐，最省事）**

```sh
su -c 'sh /data/local/tmp/crossspace/crossspace.sh 999 wx home'
su -c 'sh /data/local/tmp/crossspace/crossspace.sh 10 alipay home'
```

**C. 只有 adb（不 root）**

```sh
adb shell sh /data/local/tmp/crossspace/crossspace.sh 999 wx home
```

**D. Tasker / AutoJS / 自研 App（能发 shell 命令即可）**

```
su -c 'sh /data/local/tmp/crossspace/crossspace.sh %空间ID% %应用% %页面%'
```

**E. 想完全绕开脚本，自己拼（等价命令）**

```sh
CMD=$(cmd package resolve-activity --brief --user 999 -p com.tencent.mm \
      -a android.intent.action.MAIN -c android.intent.category.LAUNCHER | tail -n1)
am start --user 999 -n "$CMD"
```

### 2.4 接口

| 参数 | 说明 |
|---|---|
| `<user>` | 任意存在的 userId：0 / 999 / 10–30（不写死，运行时枚举） |
| `<app>` | 别名 `wx` `wechat` `alipay` `ali`，或直接写包名，或 apps.conf 自定义别名 |
| `<page>` | `home` / `scan` / `sns`(微信) / `paycode`(支付宝) / `uri:...` / 完整组件名 |
| 子命令 | `users` `apps` `env` `all` `component` |
| 环境变量 | `CROSSSPACE_RANGE` `CROSSSPACE_DRYRUN` `CROSSSPACE_FORCE` `CROSSSPACE_CONF` |

## 3. 错误码与排障

| 码 | 含义 | 现场处理 |
|---|---|---|
| 0 | 成功 | — |
| 64 | 参数错误 | 看 usage |
| 65 | user 不存在 | `-Users` 看现有空间；编号范围确认 |
| 66 | 该空间未安装应用 | 先在该空间装上，或 `-Force` 跳过检查 |
| 67 | 组件解析失败 | `-Component` 指定 / apps.conf 写 `<别名>:<页面>=<组件>` |
| 68 | 权限不足（非 0 非 2000） | 改用 adb shell 或 root |
| 69 | am 被系统拒绝 | 读错误原文；跨用户权限 → `-Su` 重试 |
| 70 | 该页面不支持直达 | 换 scheme（支付宝）或手动点 |
| 71 | 配置格式错 | 检查 `别名=包名` |
| 72/73/74 | 无 adb / 无设备 / 推送失败 | 查 USB 调试、驱动、文件锁 |
| 75/76 | 设备端执行失败 | 查 root 授权或权限 |

排查顺序建议：`-Env`（版本与身份）→ `-Users`（空间与安装）→ `-DryRun`（看解析出的命令）→ 真跑。

## 4. 跨版本兼容（ColorOS 14 / 15 / 16）

### 4.1 为什么天生跨版本

`am` 是 AOSP 的 shell 命令，`am start --user N` 只是把 `userId` 塞进 `IActivityTaskManager.startActivityAsUser` 的 Binder 调用；权限判定发生在 system_server，与 OEM 的 UI/多开私有实现无关。
ColorOS 的版本差异（多开入口、设置项、`OplusMultiAppManagerService` 的类名）都不在这条链路上。**同一份脚本三版通用**。

### 4.2 不依赖版本私有 key

- 不使用 `Settings.Global` 的 `clone_launcher_titles` 之类私钥；空间名只用于展示，取不到就用 userId/包名兜底（脚本本身就是 `UserInfo{id:名称}` 直接读）。
- 未安装检测只依赖 `pm list packages --user N`（标准命令）。
- 因此 ROM 改设置项、改名、裁剪私有 API 都不影响功能。

### 4.3 组件名不写死

主入口一律动态解析，三种策略依次尝试（脚本内已实现）：

```
cmd package resolve-activity --brief --user N -a MAIN -c LAUNCHER -p <pkg>   # 实测 ColorOS 15 可用
cmd package resolve-activity --brief --user N <pkg>
cmd package query-activities --brief --user N -a MAIN -c LAUNCHER | grep "^<pkg>/"
```

实测结果：微信 `com.tencent.mm/.ui.LauncherUI`、支付宝 `com.eg.android.AlipayGphone/.AlipayLogin`。即便某版把 Activity 改名，也只会解析结果变化，不需要改脚本。

### 4.4 版本探测与降级

- 探测：`ro.build.display.id` / `ro.build.version.sdk` / `ro.product.brand`（`crossspace.sh env` 直接打印）。
- 行为：**只做记录与提示，不拒绝执行**。探测到非 ColorOS 或非 14/15/16 时，仍然走通用 `am` 路径——这条路径本来就是 AOSP 标准能力。
- 本机 `PJX110_15.0.0.830(CN01)` / SDK 35 实测通过。

### 4.5 反面教训：LSPosed 版为什么必须分版本

原模块（ColorLink v1.1.0）的 `s()`（反编译 smali 的 L2014–2058）解析 `Build.DISPLAY` 后要求主版本 **== 14 或 16**，否则 `t()` 为 false，`onModuleLoaded` / `onSystemServerStarting` 直接不装 hook（对应 smali 的 `b/c.smali` L135/L142/L239/L521）。
注：该 APK 的反编译产物属于第三方代码，**未随本仓库分发**，文中出现的 smali 文件路径仅作为分析行号的位置标。
所以：

- ColorOS 15 上它根本不工作——与本机“调用不起”的现象吻合；
- 它依赖 `OplusMultiAppManagerService`、`ActivityTaskSupervisorExtImpl` 等**每版都可能改名/改签名**的 OEM 内部类（`changeIntentIfNeed` 在 16/17 走 `getCallingRelation`，其余走反射 `q(...)`，见 `c/f.smali` L4431–4509）；
- 只能按版本分支适配。我们的主线方案刻意避开了这一整类依赖。

## 5. 机制原理：跨用户启动到底受什么限制

### 5.1 调用链

```
am start --user N -n pkg/Activity
  → ActivityManagerShellCommand.runStartActivity
  → IActivityTaskManager.startActivityAsUser(intent, userId = N, ...)
  → ActivityTaskManagerService.startActivityAsUser
  → ActivityStarter.execute / executeRequest
  → ActivityTaskSupervisor.checkStartAnyActivityPermission(...)    # START_ANY_ACTIVITY
  → 跨用户判定（requestUserId != callingUserId）
  → PackageManager.filterAppAccess(userId)                        # 按 user 的包可见性
  → ActivityTaskSupervisor.resolveIntent / resolveActivity
  → RootWindowContainer / Task 真正启动
```

### 5.2 关键权限

| 权限 | 保护级别 | 谁能拿 |
|---|---|---|
| `START_ANY_ACTIVITY` | signature \| privileged | system / 平台签名；root 通过（用于起非 exported 组件） |
| `INTERACT_ACROSS_USERS` | signature \| installer | system、平台签名应用 |
| `INTERACT_ACROSS_USERS_FULL` | signature | system、平台签名应用（`com.android.shell` 持有） |

普通第三方应用**无法申请**这两个跨用户权限（`signature` 级），所以“给自己的 App 加个 `--user` 参数”是行不通的。

### 5.3 为什么 root 能过

权限检查按 **callingUid** 判定，CLI 只是客户端。uid 0（`Process.ROOT_UID`）在权限检查中被短路放行，因此 `su -c 'am start --user N ...'` 不依赖 shell 是否持有跨用户权限。

### 5.4 为什么 shell（adb）也能过

`com.android.shell` 是平台签名应用，AOSP 里申请了 `INTERACT_ACROSS_USERS_FULL`；`adb shell am start --user N` 的 Binder 身份是 uid 2000，因此直接可行。**这也解释了为什么本机没 root 也能跑通**（本机实测 uid=2000 成功）。

### 5.5 为什么普通 App / 无障碍不行

- 普通 App 里 `Runtime.exec("am start --user 10 ...")`：binder 身份仍是 App 自己的 uid → 被 AMS 拒绝（SecurityException），不是 CLI 被拒。
- 无障碍服务：只能注入点击/读屏，无法改变调用身份，也不能在主空间直接操作分身空间的界面。
- 所以“中转”若要无 root，只能用 Shizuku（拿到 shell 身份）——见第 7 节。

### 5.6 profile group 的影响

999 是 `CLONE` profile，与 user 0 同 profile group；PMS/部分服务对同组有豁免，但 **AMS 启动仍按 userId 处理**。实测 `--user 999` 与 `--user 10` 行为一致，均成功。

## 6. 空间机制判定：999 vs 10–30

### 6.1 判定方法

```sh
pm list users                          # 是否存在独立 UserInfo
dumpsys user                           # userType 名称
pm list packages --user N              # 该 user 是否有独立包集合
am start --user N -n ...               # 能否按 user 启动
```

### 6.2 本机证据

```
$ pm list users
UserInfo{0:机主:4c13} running
UserInfo{10:10:1010} running ... UserInfo{16:16:1010} running
UserInfo{999:MultiApp:4001010} running

$ pm list packages --user 999 | grep tencent
package:com.tencent.mm
package:com.eg.android.AlipayGphone      # 按 user 独立返回，标准用户模型
```

### 6.3 结论

| 编号 | 机制 | 说明 |
|---|---|---|
| 0 | 主用户 | owner |
| 10–30（`ymyx`） | **标准 secondary user** | 独立 UserInfo、独立装包；`--user N` 直接可用 |
| 999 | **clone profile**（`android.os.usertype.profile.CLONE`） | 与 0 同 profile group；`--user 999` 同样可用 |

不是 VirtualApp / 容器：容器方案不会有独立 `UserInfo`，也不会支持 `pm list packages --user N` 与 `am start --user N` 两个标准入口。
（`dumpsys user` 的 userType 字段本机未逐条抓取，列为待确认，但上述两个标准入口已足以判定。）

## 7. 备选路线（都比主线重，均非必需）

### 7.1 方案 0：系统“默认打开应用”（零代码，仅 999）

ColorOS 设置里可以把某应用的多开版本设为默认打开。优点：无感；缺点：只覆盖 999，不能按调用方路由，也不能覆盖 10–30，不可脚本化。

### 7.2 方案 B1：Shizuku 中转（无 root 时的等价物）

思路：常驻 App 通过 Shizuku 拿到 shell 身份（`Shizuku.newProcess` / Binder 包装），执行
`am start --user N -n ...`。
- 优点：不用 root，等效 adb shell。
- 缺点：需装 Shizuku 并每次授权；多一个常驻进程；调用方要么改造成走它的 API，要么通过它转发。
- 适用：设备不能 root、又不能一直连着 adb，且调用方 App 可改造。

### 7.3 方案 B2：无障碍服务（不可行，仅能点 UI）

无障碍只能模拟点击“多开选择框/图标”，无法指定 userId 启动，也无法在主空间操作分身空间界面。只能作为“顺带点一下”的补充。

## 10. 附录：LSPosed 路线（方案 C，仅作进阶参考）

### 10.1 它要补的四个缺口

| 函数 | 位置 | 补什么 |
|---|---|---|
| `getMultiAppResolveInfoIfNeed` | `ActivityTaskSupervisorExtImpl` | 解析阶段：系统默认只在当前 user 内解析，这里补出多开空间的 ResolveInfo |
| `resolveIntent` | `IPackageManagerBase.resolveIntent` / `Computer.resolveIntentInternal` | 在 PMS 解析入口把目标换成多开空间里对应的包/组件 |
| `changeIntentIfNeed` | `OplusMultiAppManagerService` | 真正改写 Intent：组件、包名、目标 user、`com.color.link.extra.CROSS_SPACE_SOURCE_USER` |
| `adjustCrossUserPermission` | `PermissionManagerServiceExtImpl` | 第三方调用方没有 `INTERACT_ACROSS_USERS(_FULL)`，在这里放行 |

配套还有 `skipCheckCrossUserPermission`、`getMultiAppActivityInfo`、`replaceIntentForMultiApp`、`resolveActivityForMultiApp`、`ComputerEngine.getPackageInfoInternal`。

### 10.2 hook 点表

| 进程 | 目标 |
|---|---|
| system_server | 上述 4 个函数 + `queryIntentActivitiesInternal`、`ProfilerInfo.resolveActivity` |
| com.oplus.multiapp | `chooser.MultiAppResolverActivity$MultiAppResolverTask.doInBackground` |
| com.android.intentresolver | `ResolverListAdapter`、`chooser.DisplayResolveInfo`、`TargetPresentationGetter`、`widget.OplusResolverPagerAdapterHelper` |
| launcher | `onCreate`（多开图标/标题展示） |

### 10.3 为什么这条路线成本高

1. **必须分版本**：`s()` 只认 14/16（15 直接不装），且 OEM 内部类/签名逐版变化（`changeIntentIfNeed` 在 16/17 用 `getCallingRelation`，其余走反射）。
2. **签名自校验**：反编译看到的 `b/e.d()`（L690–827）比对签名证书 sha256 与内置值，并校验 `assets/integrity.dat`（classes.dex sha256）。**重签即静默失效**——这正是改造版 `ColorLink_v1.1.0-yl.apk` 装了也不生效的原因。
3. **只覆盖 900+ 且默认 999**：`c/f.smali` 的 `E(int)` 判 `userId >= 900`，自建 10–30 空间不在设计范围，需要自己扩展。
4. 任一 OEM 大版本升级都可能要重新找 hook 点。

## 12. 阶段 1（2026-11-09）：切前台实测与结论

> 方向修正：真实需求不是“主动起某个空间的微信”，而是第三方应用发起微信/支付宝支付时，
> 系统选择框列出主空间 + 各分身的同一应用，让用户选用哪个空间的实例支付；支付宝 NFC
> 「碰一碰」也要能弹选择。这必须走 hook，`am start --user` 只能作为阶段 1 的辅助能力。

### 12.1 空间机制修正

前文按“10–30 是标准 Android secondary user”设计。实测 ColorOS 15 上并非如此：

```
UserInfo{0:机主}        Type: android.os.usertype.full.SYSTEM
UserInfo{10:10}         Type: android.os.usertype.profile.CLONE   parentId=0  Flags: INITIALIZED|PROFILE
...
UserInfo{16:16}         Type: android.os.usertype.profile.CLONE   parentId=0
UserInfo{999:MultiApp}  Type: android.os.usertype.profile.CLONE   parentId=0  Flags: ...|4000000
```

即 999 和 10–16 都是 **clone profile**，不是独立 secondary user。这直接影响切前台方案。

### 12.2 `am switch-user` / `am start-user` 实测

| 命令 | 结果 | 说明 |
|---|---|---|
| `am switch-user 10` | `Error: Failed to switch to user 10` | profile 不能成为前台 user；不是权限问题 |
| `am switch-user 0` | 无报错 | 主用户可切 |
| `am start-user -w 10` | `Success: user started` | 只后台启动，`get-current-user` 仍为 0 |
| `am start --user 10 -n com.tencent.mm/.ui.LauncherUI` | 成功，`topResumedActivity=...u10...` | 无需 switch-user 就能显示 |
| `am get-current-user` | 全程 0 | 没有真正切换用户 |

shell 身份已持有 `INTERACT_ACROSS_USERS_FULL`（`dumpsys package com.android.shell` 可见），
所以失败原因是 **user type（PROFILE）限制**，root 也无法绕过；本机无 `su`，全程 uid=2000 完成。

### 12.3 真正的“切前台”

`am start --user N` 起的 Activity 会直接显示在当前 display 上（current user 不变）。
- 10–16：force-stop 后冷启动直接显示，不弹任何框。
- 999：ColorOS MultiApp 会拦截冷启动，弹出
  `com.android.intentresolver/.ChooserActivityLauncher`（Intent `ACTION_CHOOSER`，
  `mCallingUid=2000`），选项为「微信 / <用户名>.999 / 记住我的选择」。勾选“记住我的选择”
  并点 999 一次后，后续 `am start --user 999` 直接进入 `u999`，不再弹窗。

回主空间：`input keyevent 3`（KEYCODE_HOME）→ `topResumedActivity=...u0 com.android.launcher/.Launcher`。
不做 `switch-user`，所以主空间任务栈和进程全部保留，无副作用。

## 13. 阶段 2：跨空间支付选择器（设计 + 最小原型）

> 目标：别的应用发起微信/支付宝支付时，系统选择框列出 **主空间 0 + 999 + 10–30** 里装的同名应用，
> 选中哪个就用哪个空间的实例把支付走完；不做"我们主动发 intent"。

### 13.1 先给结论

1. **C15 上不能"照抄原模块"**：原模块靠 Oplus 的 `ActivityTaskSupervisorExtImpl#getMultiAppResolveInfoIfNeed`、
   `ActivityStarterExtImpl#getMultiAppActivityInfo` 等扩展点，C15 的 `oplus-services.jar` 里这些方法**不存在**。
   C15 换成了 `com.android.server.am.OplusMultiAppManagerService` 一套新 API（下面列出实测签名）。
2. **可以照搬的是架构**：候选生成 → 候选选择 → 意图改写 → 跨 user 权限放行，这四个环节缺一不可。
3. **C15 上最省力的注入点不是 AOSP 的 PMS/AMS，而是 ColorOS 自己的多开服务**：
   系统自带的「0/999」选择器就是它驱动的，复用它的 UI 与启动路径，只需把候选集合从 {999} 扩到 {999, 10–30}。
4. 一套代码 + 运行时探测（按类名/方法名枚举 hook，找不到就跳过并降级），**不按 ColorOS 版本分叉**。
5. NFC：普通 scheme/NDEF 拉起可以走同一选择器；HCE APDU 属于 NFC 控制器层的 AID 路由，
   **在 Intent 层拦不到**，需要额外前提（详见 13.7）。

### 13.2 C15 的多开链路（实测反编译证据）

`/system/framework/oplus-services.jar` 内含 `com.android.server.am.OplusMultiAppManagerService`
（system_server 内加载）。实测反汇编出的关键方法：

| 方法 | 签名 | 作用（推断） |
|---|---|---|
| `getChooserIntent` | `(Intent, String, String, int, int[], int) → Intent` | 构造多开选择器 Intent（候选 user 数组 + 选择模式） |
| `changeIntentIfNeed` | `(int[], ActivityInfo, Intent, String, int, SafeActivityOptions, String, ActivityTaskSupervisor, int, int) → Intent` | 启动前改写 intent（加 chooser / 改 user），即"意图改写"环节 |
| `changeUserIdFromResolveInfo` | `(int, ResolveInfo) → int` | 从 ResolveInfo 反推目标 user，即"选中后传 user"环节 |
| `filterResolveInfoForMultiApp` | `(Intent, List, int, int)` | 对候选列表做多开过滤/补充，即"候选生成"环节 |
| `getMultiAppList` | `(int) → List` | 某空间/包的多开实例清单 |
| `isMultiAppUserId` / `getCorrectUserId` | `(int) → Z` / `(int) → int` | 是否多开 user、纠正到真实 user |
| `setOplusUserId` | `(ActivityInfo, Intent, int)` | 把目标 user 写到 ActivityInfo/Intent 上（Oplus 私有标记） |
| `getAllHomeResolveInfo` | `(int) → List` | 取某 user 的 launcher 入口 ResolveInfo |
| `isMultiApp` | `(int, String) → Z` | 判断 (userId, pkg) 是否多开实例 |

常量里还有 `PACKAGE_WX`、`PACKAGE_ALIPAY`、`sChooserComponentName`、`EXTRA_SKIP_REPLACE_INTENT`、
`EXTRA_INTERCEPT_START_ACTIVITY`、`USER_OPERATION_TIMEOUT_MS`、`sActionListRedirect2MultiAppUser` 等。
这说明 ColorOS 的多开选择是**按包白名单 + 选择器组件 + 特殊 extra** 实现的，不是通用 AOSP 逻辑。

与原模块（C14/C16）的对应关系：

| 原模块 hook（C14/C16） | C15 是否存在 | 结论 |
|---|---|---|
| `ActivityTaskSupervisorExtImpl#getMultiAppResolveInfoIfNeed` | 不存在 | C15 不装这条 hook，原模块在 C15 完全不生效 |
| `ActivityStarterExtImpl#getMultiAppActivityInfo` | 不存在 | 同上 |
| `OplusMultiAppManagerService#replaceIntentForMultiApp` | 不存在（改名/重构） | C15 对应 `changeIntentIfNeed` / `getChooserIntent` |
| `OplusMultiAppManagerService#resolveActivityForMultiApp` | 不存在 | C15 对应 `changeUserIdFromResolveInfo` / `filterResolveInfoForMultiApp` |

即：**C15 不是"少一个版本判断"，是整套 Oplus 扩展点被替换**，必须重新对齐方法名。

### 13.3 注入层怎么选（三个候选的取舍）

| 注入点 | 能拿到 | 代价 / 风险 | 适用性 |
|---|---|---|---|
| **A. Oplus 多开服务**（`changeIntentIfNeed` / `getChooserIntent` / `filterResolveInfoForMultiApp`） | 原始 intent、候选列表、目标 user 数组、上下文 `ActivityTaskSupervisor` | 是厂商私有 API，版本间改名；需运行时探测签名 | **首选**：直接复用 ColorOS 选择器，最小改动、与系统 UI 零冲突 |
| **B. PMS** `ComputerEngine#queryIntentActivitiesInternal`（3 个重载：`(I,S,J,I)`、`(I,S,J,I,I)`、`(I,S,J,J,I,I,I,Z,Z)`） | 所有查询结果，能追加/伪造 ResolveInfo | 调用量极大，任何异常都直接拖死 system_server；返回 List 可能不可变；需要防递归 | 作为兜底：Oplus 点找不到时用 |
| **C. AMS** `ActivityTaskSupervisor#resolveIntent` / `resolveActivity` / `startActivityAsUser` | 最终解析结果、可强制改写成 chooser | 语义最贴近"启动"，但改错会导致所有应用无法启动；AMS 内部链路复杂 | 最后手段，只用于兜底强制 chooser |

**推荐组合**：
1. 先 hook A 的 `changeIntentIfNeed`（启动前改写）与 `filterResolveInfoForMultiApp`（候选列表），把 10–30 的实例补进去；
2. 若 A 在 C15 上方法签名与实测不符（探测失败），退回 B：在 `queryIntentActivitiesInternal` 里按 user 追加候选；
3. C 只用于"必须强制弹框"的场景，且用 ThreadLocal 防递归、失败即放行。

### 13.4 ResolveInfo 伪造与 user 传递（关键坑）

- **只动 user，不动包身份**：伪造候选时保留原 `ResolveInfo` 的 `activityInfo` / `applicationInfo`（包名、processName、权限），
  只额外挂"目标 user"。**不要**直接把 `applicationInfo.uid` 改成 `UserHandle.getUid(targetUser, appId)`：
uid 一改，PMS 的 `filterApplication`/包可见性检查会用错误 uid 去查，轻则条目被过滤，重则目标进程以错误 uid 起不来。
- **user 的两种携带方式**：
  - AOSP 风格：`ResolveInfo.userHandle`（选中的 `ResolverActivity` 用它决定 `startActivityAsUser` 的 user）；
  - Oplus 风格：`setOplusUserId(ActivityInfo, Intent, user)` + `changeUserIdFromResolveInfo(userId, ri)`（C15 实测存在）。
  C15 上优先用 Oplus 的 `setOplusUserId`，因为它跟系统自带选择器的读取方式一致；同时兜底写 `userHandle`。
- **选中后怎么把 user 带下去**：目标 Activity 用显式 component + `--user` 语义启动。实测 `am start --user N`
  在 shell 身份下可行（shell/intentresolver 均有 `INTERACT_ACROSS_USERS_FULL`），说明 AMS 层不拦；
  模块里做等价的事：`startActivityAsUser(intent, options, UserHandle.of(N))`，或在 Oplus 改写后的 intent 上带 user。
- **权限放行**：`PackageManagerServiceExtImpl#skipCheckCrossUserPermission`（原模块 hook 的
  `adjustCrossUserPermission`）补的是"跨 user 的 resolve/启动被 PMS 的跨用户检查误杀"这一环；
  C15 上若走 Oplus 服务（它本身就是 system_server 内部逻辑，uid 是 system），通常不需要额外放行，
  但 B 方案（PMS 注入）必须补这一层，否则"看得到点不进去"。

### 13.5 原模块四个函数各补什么缺口（从 smali 读出，仅作参考）

| 函数 | 补的缺口 | 我们对应的实现位置 |
|---|---|---|
| `getMultiAppResolveInfoIfNeed` | 把普通 ResolveInfo 标记/改写成"多开候选"，让后续解析认可这个实例 | 候选生成（A 的 `filterResolveInfoForMultiApp` 或 B 的 query 追加） |
| `resolveIntent` | 决定"这个 intent 该由哪个 user 的实例处理"，补 10–30 的解析路径 | 候选选择（A 的 `changeUserIdFromResolveInfo`） |
| `changeIntentIfNeed` | 把 intent 改写成 chooser / 换 component / 带上目标 user | 意图改写（A 的 `changeIntentIfNeed` / `getChooserIntent`） |
| `adjustCrossUserPermission`（`skipCheckCrossUserPermission`） | 让跨 user 的 resolve/启动不被权限检查杀掉 | 权限放行（B/C 方案才需要；A 方案通常不需要） |

四个环节是完整闭环：**候选生成 → 候选选择 → 意图改写 → 权限放行**。少任何一个，表现分别是
"框里没有" / "有但点进去还是主空间" / "点进去崩溃或跳到别的应用" / "直接报 Permission Denial"。

### 13.6 跨版本（C14 / C15 / C16）与冲突去重

- **不按版本分叉**：一套模块代码，启动时对候选类做"探测式 hook"——
  用 `Class.forName` + 反射枚举同名方法，找到就 hook，找不到就记录并降级到下一层（A→B→C）。
- **版本探测**：`ro.build.display.id`（如 `PJX110_15.0.0.830(CN01)`）+ `Build.VERSION.SDK_INT`；
  探测到未知版本**不拒绝执行**，走通用路径（B 方案），并在日志标注 `unknown-version fallback`。
- **与 ColorOS 自带选择器的冲突**：
  - 999 已被系统列一次，我们再补一次会**重复**。去重键用 `(targetUser, componentName)`，
    追加前先扫一遍现有候选，命中就不加。
  - 不接管/替换系统选择器 UI（不 hook `OplusResolverPagerAdapterHelper` 的渲染），只扩候选集合，
    这样系统升级改了 UI 也不会被我们带崩。
  - ColorOS 有"记住我的选择"缓存（实测：勾选后 999 不再弹框）。调试时若看不到选择框，
    先清 `com.android.intentresolver` 的数据或换一个未缓存的应用/action 复测。
- **10–16 与 999 的差别**：实测 999 在 `com.oplus.multiapp` 注册表内、10–16 不在；
  因此 999 走系统原生链路，10–30 必须由我们注入候选——这也是为什么去重必须做。

### 13.7 支付宝「碰一碰」NFC 调研结论

实测抓到的链路（ColorOS 15 / 一加 PJX110）：

| 触发方式 | 实测证据 | 能否介入 |
|---|---|---|
| **NDEF / scheme 拉起**（`alipays://`、`weixin://`） | resolver 正常解析到 `com.eg.android.AlipayGphone` / `com.tencent.mm` | **能**：与普通支付同一条 Intent 链路，选择器方案直接覆盖 |
| **NFC NDEF_DISCOVERED**（`application/com.alipay.mobile.nfc`） | 系统 NFC 服务解析 tag 后按 NDEF 记录发 Intent | **能，但有前提**：需在候选注入层同样处理 `ACTION_NDEF_DISCOVERED` 的 intent；且要确认 NFC 服务是否直接指定了包名 |
| **TECH_DISCOVERED / HCE APDU** | 注册了 `HCEOverSeaPayApduService`（海外 HCE） | **不能（在 Intent 层）**：APDU 由 NFC 控制器按 AID 路由到已注册的 `HostApduService`，发生在 AMS/Intent 之前；同一 AID 在同一时刻只能有一个注册者，跨 user 无法并存。要介入只能 hook `com.android.nfc` 的 AID 路由/HostEmulationManager，属于另一个模块，前提是系统允许同一 AID 多注册（通常不允许） |
| **BLE / 扫码** | 有 BLE scan receiver | 不是 Intent 链路，选择器方案不覆盖 |

结论：**"碰一碰"要分两种理解**——
- 碰一碰后由系统拉起支付宝（NDEF/scheme）→ 可以进选择器；
- 碰一碰直接进 HCE 支付（APDU）→ **不能**，这是 NFC 控制器层的进程绑定，不是应用层选择。
待实机验证：用带支付宝 NFC 标签的贴纸触发一次，抓 `dumpsys activity intents` / logcat 看最终是
`ACTION_NDEF_DISCOVERED` 还是 HCE service 绑定。

最小目标：主空间发起 `alipays://` / `weixin://` 时，选择框里除系统自带条目外，多出一个

#### 13.8.1 实测记录（ColorOS 15 / OnePlus PJX110 / SDK 35）

**结论：链路已跑通。** 主空间发起支付宝跳转时，选择框里出现两个「支付宝」，第二个以 `u15` 启动。

| 步骤 | 命令/操作 | 实测结果 |
|---|---|---|
| 模块加载 | 重启后查 logcat | system_server 侧出现 `[CrossSpaceProto] ...`，说明 `android` 包已加载模块 |
| 注入生效 | `adb shell am start -a android.intent.action.VIEW -c android.intent.category.BROWSABLE -d "alipays://platformapi/startapp?appId=20000067"` | `mCurrentFocus = u0 com.android.intentresolver/ChooserActivityLauncher` |
| 候选出现 | `uiautomator dump` | 两个「支付宝」+「记住我的选择」+「取消」 |
| 点第 2 个 | `adb shell input tap <坐标>` | `mCurrentFocus = Window{... u15 com.eg.android.AlipayGphone/com.ali.user.mobile.loginupgrade.activity.LoginActivity}` |
| 点第 1 个（前一轮） | tap 第一个条目 | `mCurrentFocus = u0 com.eg.android.AlipayGphone/...XRiverActivity`（主空间实例） |

关键 logcat 证据：

```
[CrossSpaceProto] inject + com.eg.android.AlipayGphone/com.eg.android.AlipayGphone.AlipayLogin user=15
[CrossSpaceProto] inject done, total=2
[CrossSpaceProto] filterResolveInfoForMultiApp(..., List[2]{RI{AlipayLogin,u=0}, RI{AlipayLogin,u=15}}, ...)
```

说明注入点选在 **PMS `ComputerEngine#queryIntentActivitiesInternal`**（13.3 的 B 方案）是有效的：
候选进了列表、系统选择器按原样渲染、点选后由 Oplus/AMS 按 `userHandle` 正确路由到 u15。

**踩到并已修复的坑（原型代码里都有对应处理）：**

1. **跨用户检查误杀**：hook 跑在发起方 binder 线程，`Binder.getCallingUid()` 仍是被调应用（非 system），
   PMS 的跨 user 检查会抛 `SecurityException`（表现为 `inject err: InvocationTargetException`）。
   修复：调用前 `Binder.clearCallingIdentity()`，`finally` 里 `restoreCallingIdentity()`。**这一条是 B 方案
   的必选项，等价于原模块的 `adjustCrossUserPermission`。**
2. **`setOplusUserId` 的副作用**：给候选调 Oplus 的 `setOplusUserId(ActivityInfo, Intent, 15)` 后，
   `user 0` 的支付宝被置为 `enabled=0`（disabled），`alipays://` 在主空间直接解析失败。
   恢复：`pm enable --user 0 com.eg.android.AlipayGphone`。**原型已彻底删除该调用，只写 `userHandle`
   即可，不再碰 Oplus 的注册表。**
3. **`ResolveInfo` 复制共享 `ActivityInfo`**：直接 `new ResolveInfo(ri)` 后两个条目共享同一个
   `ActivityInfo` 引用，改写 uid/flag 会互相污染。原型只改外层 `userHandle`，不动 `ActivityInfo.applicationInfo.uid`。
4. **APK 解析竞态**：`adb install --no-incremental -r` 后**立刻**重启，偶发
   `PackageParserException: Failed to parse ...` / `IOException: Failed to load asset path`，模块不加载。
   再重启一次即恢复。已写进 `proto/README.md`。
5. **`alipays://` 清单要求 BROWSABLE**：shell 触发必须带 `-c android.intent.category.BROWSABLE`，
   否则 `am start` 报 "unable to resolve"（浏览器发起天然带该 category，所以真实场景不受影响）。

**已观察到但未在原型处理的行为（留给全量阶段）：**

- ColorOS 自己只为 **999** 出候选（`isMultiAppUserId(15)` 实测返回 `false`，15 不在其注册表）。
  即：系统会把 999 列一次，我们再加 15；若以后配置里同时含 999 与 999 自带的项，**必须按
  `(targetUser, componentName)` 去重**（13.6 已写）。
- 勾过「记住我的选择」后，同一 intent 会被系统直接路由（实测 `weixin://` 直接进 999，不再弹框）。
  复测前需清 `com.android.intentresolver` 数据或换 action。
- 原型只处理 **发起方 `userId == 0`** 且目标 user 硬编码 `15`；**10–30 全量、多应用配置、NFC** 未做。

**未验证项（如实标注）：**

- 支付宝「碰一碰」NFC 实机触发（未用真实 NFC 标签跑过），因此 13.7 中 NDEF 可介入仍是**静态结论**；
  HCE APDU 不可介入是依据 AID 路由机制推断，同样未实机复现。
- 微信支付：`weixin://` 被「记住选择」缓存后未复测注入（只验证了支付宝；注入逻辑对包名无差别）。

#### 13.8.2 改版：自建选择器（2026-11-09，阶段 2 全量）

13.8.1 那版把候选追加进**系统**选择器，链路能通，但有三个绕不过去的问题（都是实测）：

| 问题 | 表现 |
|---|---|
| ColorOS 别名统一化 | `getMultiAppAlias(pkg)` 生成「<用户名>.999」，把我们写的「微信 · 空间12」覆盖掉，10–16 分不出来 |
| 系统 Resolver 排序 | 同一组件多 user 的比较器不满足传递性，`TimSort` 抛异常，选择器直接不出现 |
| 999 重复 | 系统自己列一次 999，我们再追加一次就重复 |

于是把 UI 和候选都收回模块自己手里：**hook 外部启动 → 枚举各空间 → 拉起自建选择器 → 选中后以 system 身份
`startActivityAsUser(intent, UserHandle.of(N))`**。

```
外部 intent
  └─ ATMS#startActivityAsUser（hook）
       ├─ 过滤：发起方是外部应用（非 system/launcher/本模块）、目标解析到微信/支付宝、≥2 个空间装有
       ├─ 排除：调用方就是微信/支付宝自己（否则分身起来后自己再发深链，会叠出第二个选择器）
       ├─ 枚举：ALL_USERS=0 + 999 + 10..30，逐个 queryAsUser，按 (pkg, user) 去重
       ├─ 启动 com.crossspace.proto/.SpaceChooserActivity，extras 带原始 intent + 候选
       └─ 选中回放：clearCallingIdentity + system Context#startActivityAsUser(intent, UserHandle)
```

两个必须记住的坑：

1. **别改 `startActivityAsUser` 的 int 形参当 userId**。ColorOS 的重载顺序与 AOSP 不同，
   改错下标不会报错，只是静默落在 u0（实测：点「空间15」后 `topResumedActivity=u0 ... AlipayLogin`，
   日志里 `replay ok: user=15` 却是成功的）。必须走 `ContextImpl#startActivityAsUser(Intent, UserHandle)`。
2. **必须排除目标应用自己发起的 intent**。微信在 999 起来后会继续发
   `WXCustomSchemeEntryActivity → MMWebViewUI` 这类内部跳转；按「外部应用拉起微信」的规则再走一遍，
   就会在新拉起的空间上叠一层选择器，表现为「点了空间退不出去」。
   判据用调用方 uid 的 appId 与 `WATCH_PKGS` 相同（不受 user 影响）。

实测（ColorOS 15 / PJX110 / SDK 35，2026-11-09）：

| 用例 | 候选 | 点选后 |
|---|---|---|
| `alipays://` → 空间15 | 支付宝 · 主空间 / 999 / 10–16（9 项，图标正常） | `u15 com.eg.android.AlipayGphone/.AlipayLogin` |
| `weixin://` → 空间999 | 微信 · 主空间 / 999 / 10–16（9 项） | `u999 com.tencent.mm/...MMWebViewUI` |
| `weixin://` → 空间12 | 同上 | `u12 com.tencent.mm/.plugin.base.stub.WXCustomSchemeEntryActivity` |
| `weixin://` → 主空间 | 同上 | `u0 com.tencent.mm/...MMWebViewUI` |

补充（2026-11-10 复测）：选择器**已弹出时再触发第二种支付**，同一实例经 `onNewIntent` 刷新为对应应用的
9 项候选（图标同步切换），点「空间999」仍正确落到 `u999 .../MMWebViewUI`——连续触发不会拿着上一次的列表点错空间。
（相关实机截图未随仓库分发。）

反向验证：桌面点微信/支付宝图标 → 直接以 u0 打开、不弹选择器（`isExternalPkg()` 排除了 launcher、systemui、
intentresolver、`com.oplus.*`、`com.coloros.*`），日常使用不受打扰。

2026-11-10 追加两条实测：

- **NFC 碰一碰**：碰一碰拉起支付宝后选择器正常出现，点选不同空间由对应空间的支付宝响应——13.7 里
  「NDEF 拉起可介入」的静态推断得到实机验证。
- **图片分享（ACTION_SEND）→ 微信**：u0 / u10 / u12 / u15 / u999 逐个点选，`topResumedActivity` 分别落在
  对应空间的 `com.tencent.mm/.ui.transmit.SelectConversationUI`，回放日志 `replay ok: user=N` 与选择一致。

  期间修掉一个候选列表缺陷：去重键从 `(包名, Activity, user)` 改为 `(包名, user)`。分享场景下微信在同一空间
  能解析出 4 个入口（`ShareImgUI` / `ShareToTimeLineUI` / `WXEntryActivity`…），旧规则会列出 54 条、同一空间
  重复 5 条「微信 · 主空间」，既难选也容易点错行；改成每空间每应用一条后是 18 条（2 应用 × 9 空间）。
  实测：即便如此，只有按行文本精确核对过的点选才会落到正确空间，靠像素估坐标遇到长列表会点错——
  排查期一度出现「点了 12 却进了 u11」的现象，就是点错行，不是回放出错。

工程侧另外三条（都写进 `proto/README.md`）：

- **构建**：build-tools 里的 R8 8.2.2 对「带外部实例的匿名内部类」抛 NPE（只指向 `SpaceChooserActivity$1.class`，
  做过最小复现）；`d8 --no-minification` 也是非法参数。build.ps1 已改成优先用 Android Studio 自带的新版 `r8.jar`。
- **`exported="true"`**：选择器要能被 system_server 拉起；`false` 时起不来。它只读自己 intent 里的 extras，
  被第三方拉起来只会显示空列表并 `finish()`。
- **`singleInstance` + `onNewIntent`**：连续两次支付跳转会被投递到同一个实例，不重建候选就会拿着上一次的列表点错空间。

仍属边界：每次必弹（不提供「记住我的选择」）；`WATCH_PKGS` 硬编码微信/支付宝；NFC 的 NDEF/HCE 未实机验证。

#### 13.8.3 图片分享「点任何空间都进 999」的定位与修复（2026-11-10）

现象：相册里分享一张图给微信，选择器列出 9 条「微信 · 各空间」，**点哪一条都落到 u999**。

排查推翻了三层假设，最终三条原因叠加：

1. **ColorOS 会把第三方发起的微信启动静默改到 u999。**
   曾经给「目标空间 = 调用方空间」加了一条快捷分支（清掉 extras 后直接 `return`，让系统原生链路去处理）。
   实测 `u999 com.tencent.mm/.ui.tools.ShareImgUI ... removeAppToken ... destroyed`——主空间那次被 ColorOS
   换到了 999 空间。**该分支已删除**，现在所有空间统一由模块回放。
2. **`ShareProvider` 包装分享 URI 是负收益（包可见性）。** 早期为了绕开跨 user 读媒体，把
   `content://media/...` 包成 `content://com.crossspace.proto.share/f?u=...`。实测日志：
   `E ActivityThread: Failed to find provider info for com.crossspace.proto.share`（u0 微信、u12 微信都连报），
   微信 200ms 内关窗。原因是 Android 11+ 包可见性：微信 targetSdk 高且没有指向我们的 `<queries>`，
   AMS 根本不建 provider 记录。→ `wrap1()` 改为恒等（直接返回原 URI），provider 保留但不再使用。
3. **system 身份不能给别人授 URI 读权限。**
   `W UriGrantsManagerService: For security reasons, the system cannot issue a Uri permission grant to ...; use startActivityAsCaller() instead`。
   改为**以本模块包身份授权**（本模块天生持媒体权限）：`ensureOwnMediaPerm(user)` 先确保自己在目标空间有
   `READ_MEDIA_IMAGES`，再 `grantViaOwnApp()` 用 `createPackageContextAsUser("com.crossspace.proto", ...)`
   逐条 `grantUriPermission(微信, uri, FLAG_GRANT_READ_URI_PERMISSION)`。

最终回放（`Main.java`）：`p.setResult(0)` → `postDelayed(900ms)` → `clearCallingIdentity` 内
`systemContext()` + `userHandleOf(tu)` → `ensureOwnMediaPerm(tu)` → `grantViaOwnApp(fi, tp, tu)` →
`ContextImpl#startActivityAsUser(intent, UserHandle)` → 落盘 `replay ok sys user=N`。

两个工程坑（都踩过）：

- **回放延迟必须是 900ms 左右，不能拉到 2000ms。** 2000ms 时选择器 `finish()` 已过、发起方完全退到后台，
  system 身份的后台启动被系统按 BAL 规则静默丢弃（`startActivityAsUser` 不抛异常、日志仍打 `replay ok`，
  但 `dumpsys` 里连微信 task 都不出现）。900ms 时选择器还在前台，起步成功。
- **`BOOT rev=` 才是「新版有没有被加载」的唯一判据。** 出现过 MD5 与本地 APK 完全一致、dex 里也搜得到新字符串，
  但落盘日志仍是上一版 rev 的情况——LSPosed 加载的是旧 dex。重装 + `kill -9 system_server` 后 rev 变了才生效。

修复后实测（相册看图页 → 分享 → 微信 → 发送给朋友 → 点行）：

| 点选 | 落盘日志 | 页面 |
|---|---|---|
| 「微信 · 主空间」 | `own perm ok u=0` / `owngrant com.tencent.mm u0 <media uri>` / `replay ok sys user=0` | `u0 com.tencent.mm/.ui.transmit.SelectConversationUI` |
| 「微信 · 空间999」 | `replay ok sys user=999` | `u999 .../.ui.transmit.SelectConversationUI` |
| 「微信 · 空间12」 | `replay ok sys user=12` | `u12 .../.ui.transmit.SelectConversationUI` |

回归复测（同一次改动之后）：支付宝 `alipays://` → 主空间/999/12 分别落 `u0` / `u999` / `u12`
`com.ali.user.mobile.loginupgrade.activity.LoginActivity`，日志 `replay ok sys user=0/999/12`；无回归。
（主空间分享成功后的「选择一个聊天」实机截图未随仓库分发。）

残余风险：`com.crossspace.proto` 未安装到 999 空间，`grantViaOwnApp` 在 999 那条路径上等于空转
（本次 999 实测通过是因为该空间微信对媒体 URI 已具备可读权限）；若今后 999 出现读不到图，需要先往 999 装模块包。

### 13.9 风险与回退

- system_server hook 异常会导致**软重启循环**。回退方式：
  1. `adb shell su -c "touch /data/adb/modules/<模块id>/disable"`（KernelSU 禁用模块）；
  2. 或卸载 APK 后在 LSPosed 管理器取消勾选；
  3. 仍循环则进 recovery 删 `/data/adb/modules/<模块id>`。
- 调试期不开"接管 UI"，只做候选注入，保证最坏情况只是"没多出选项"，而不是整机不可用。
- 每次改动后需要重启 system_server（`su -c "kill -9 $(pidof system_server)"`，框架会自拉起）。

## 13.9 图片分享「主空间微信打不开」的根因与解法（2026-11-10 v0.3）
13.9.1 根因
微信 `ShareImgUI` 收到 `ACTION_SEND` 后，点「发送给朋友」会在 `onSceneEnd` 里再 `startActivity(MsgRetransmitUI, EXTRA_STREAM)`。
Android 15 在 `ActivityStarter$Request.resolveActivity` 里新增
`enforceRequireContentUriPermissionFromCallerOnIntentExtraStream`：**发起方（也就是 u0 的微信自己）必须真的持有那个 content:// 的读权限**，
否则抛 `SecurityException: UID <微信uid> does not have permission to content://media/external_primary/images/media/... [user 0]`，微信直接崩。
而这条链上能"发放"权限的只有原始持权方（相册），system_server 以 uid 1000 身份 `grantUriPermission` 会被
`UriGrantsManagerService` 明确拒绝（"For security reasons, the system cannot issue a Uri permission grant ... use startActivityAsCaller() instead"）。
13.9.2 为什么「收藏 / 朋友圈 / 微信状态」正常
崩溃栈只出现在 `com.tencent.mm.ui.tools.ShareImgUI.onSceneEnd → startActivity(MsgRetransmitUI, EXTRA_STREAM)` 这一条。
`微信状态 / 收藏 / 朋友圈` 是 ShareImgUI 内部直接调用、不经"带 EXTRA_STREAM 的二次 startActivity"，所以根本不触发该校验（推断，未逐项抓栈）。
13.9.3 解法（最终落到 v0.3）
- 只对「目标空间 = 主空间 + 目标包 = 微信」这一单，把 `EXTRA_STREAM` **和 `ClipData`** 里的 `content://media/...`
  替换成 `file://<MediaStore _data 真实路径>`（`toFileUri()` 用系统上下文查 `_data`）。
  微信本来就有读媒体存储的权限，按路径读不经过 UriGrant 校验，二次 start 也就不再崩。只改 EXTRA_STREAM 不改 ClipData 不行（实测仍崩）。
- 其它空间（999/10–16）保持原路径（`startActivityAsCaller` + `startActivityAsUser`），实测 u12 仍正常。
- `startActivityAsCaller` 仍然保留：它能让主空间这一单的**外层**启动不再抛异常；但它会把落点改到 u999（ColorOS 应用分身策略），
  所以主空间现在不再走它，改走 file:// 路径 + 直接 `startActivityAsUser(0)`。
13.9.4 实测结果（PJX110 / ColorOS 15 / SDK 35）
u0 微信：`topResumedActivity=u0 com.tencent.mm/.ui.transmit.SelectConversationUI`；
u12 微信回归：`topResumedActivity=u12 ... SelectConversationUI`。
13.9.5 已知限制
- 仅覆盖单张/单个 URI 的 `ACTION_SEND`；`ACTION_SEND_MULTIPLE`（多选分享）未做替换，仍走原链路（主空间会崩）。
- 依赖 `/sdcard` 路径对 u0 微信可读；文件在应用私有目录时不适用。
- alipays:// 由 shell `am start` 触发不会弹自建选择器（caller=shell 被过滤），碰一碰/NFC 路径本次未回归实测。
